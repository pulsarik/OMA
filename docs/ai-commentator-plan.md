# План ИИ-комментатора Omaha Hi-Lo

Статус: предложение к реализации. Проверка документации сервисов: 18 октября 2026 года. Код функции пока не реализован; реальные задержки и качество голоса не измерены.

## 1. Продуктовое решение

За столом появляется ИИ-комментатор: он получает публичные факты игры, самостоятельно формулирует короткую реплику и произносит её синтезированным голосом. Каждая реплика создаётся для конкретного события. Заранее записанного каталога фраз нет.

Характер: спокойный покерный обозреватель, наблюдательный, доброжелательный, с редким лёгким юмором. Он замечает динамику партии, но не даёт советов о следующем ходе и не приписывает игрокам намерений.

Название в интерфейсе: «ИИ-комментатор» / “AI commentator”. «Ведущий» уже используется для создателя стола.

Первая версия работает после завершения раздачи, в игре с людьми и с ботами. Затем можно добавить редкие комментарии во время торгов. Разговоры игроков не передаются в ИИ: для приоритета человеческой речи достаточно сигнала голосовой активности.

## 2. Выбранные сервисы

| Назначение | Выбор | Основание |
| --- | --- | --- |
| Генерация реплики | OpenAI Responses API, `gpt-5.4-mini`, `reasoning.effort: none` | Короткая задача с готовыми фактами; модель поддерживает структурированный ответ. Качество именно покерных реплик проверяем на наборе сценариев. |
| Синтез речи | ElevenLabs TTS API, `eleven_multilingual_v2` | Поддержка русского и английского, выразительная речь; для комментариев после раздачи можно отдать приоритет голосу. |
| Кандидат для сравнения скорости | ElevenLabs `eleven_flash_v2_5` | Поддерживает русский; сравнить ту же подборку реплик, если основная модель не укладывается в задержку. |
| Доставка | Существующий WebSocket + HTTP-аудио с нашего сервера | Одно событие и один синтез на язык для всего стола. У каждого игрока собственная громкость и язык. |

В OpenAI используем JSON Schema для ответа. Поддержка схемы не гарантирует истинность текста: факты всё равно ограничиваем и проверяем. [OpenAI Docs: GPT-5.4 mini](https://developers.openai.com/api/docs/models/gpt-5.4-mini), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Multilingual v2 выбран как начальная модель для прослушивания, а не как доказанный победитель по качеству. В актуальном каталоге ElevenLabs есть более новые v4/v4 Turbo: их можно включить в прослушивание, но оснований обещать лучший русский покерный голос без проверки нет. Заявленные поставщиком миллисекунды для быстрых моделей не включают всю нашу цепочку генерации и доставки. [Модели ElevenLabs](https://elevenlabs.io/docs/overview/models/).

Синтез первой версии: `POST /v1/text-to-speech/{voice_id}`, результат MP3. Полностью получить короткое аудио, затем разослать событие готовности. Потоковое воспроизведение добавлять только при измеренной необходимости. [ElevenLabs Create speech](https://elevenlabs.io/docs/api-reference/text-to-speech/convert).

Конкретный `voice_id` выбрать на первом этапе из доступных аккаунту голосов с русским произношением. Прослушать 3 кандидатов на одинаковых 20 фразах: хай/лоу, олл-ин, четверть банка, имена, числительные, спокойный итог, крупная победа. Выбрать один основной голос; для английского проверить этот же голос, при необходимости настроить отдельный. Идентификатор хранится в конфигурации. Непрослушанный голос нельзя честно объявить окончательно выбранным. Рекомендация выбирать голос под язык есть и у поставщика. [Выбор голоса и языка](https://elevenlabs.io/docs/overview/capabilities/text-to-speech).

## 3. Какие события комментировать

Начальные пороги — продуктовые настройки, их корректируем после игровых сессий.

| Приоритет | Событие | Проверяемое условие |
| --- | --- | --- |
| 100 | Победа в партии | Игра подтверждает единственного оставшегося игрока; досрочное завершение отличаем от победы. |
| 90 | Игрок забрал хай и лоу | Один игрок выиграл обе части соответствующего оспариваемого банка. Весь банк называем выигранным только после проверки всех побочных банков и возвратов. |
| 80 | Вылет игрока | После окончательного распределения фишек игрок выбыл по правилам игры. |
| 70 | Крупный банк | Оспариваемый банк от 20 текущих больших блайндов; возврат неуравненной ставки не увеличивает его. |
| 60 | Смена лидера | Новый единоличный лидер по стеку после выплаты; ничья не считается единоличным лидерством. |
| 50 | Необычное разделение | Например, четверть конкретного банка; не переносим долю одного побочного банка на весь результат. |
| 40 | Серия результатов | Подтверждённая серия за последние раздачи; выигрыш банка и положительный чистый результат считаем разными фактами. |

Обычное разделение хай/лоу само по себе слишком частое событие. Не озвучиваем его каждый раз. Обычные чеки, коллы, фолды, старт каждой раздачи и каждую смену улицы пропускаем.

Пример желаемого результата: «И хай, и лоу уходят Анне. После этой раздачи она выходит в лидеры». Это пример стиля, а не заготовка для воспроизведения; оба утверждения должны быть подтверждены.

## 4. Частота и память

- Один выбранный повод на раздачу; связанные подтверждённые факты можно объединить в одной реплике.
- Режим стола по умолчанию: пауза минимум 90 секунд и минимум две завершённые раздачи между обычными комментариями. Это верхняя граница частоты, а не обязательство говорить.
- Ориентир для настройки: одна реплика на 2–4 раздачи, если есть интересные события.
- Завершение партии может обойти обычную паузу, но никогда не накладывается на уже звучащую реплику.
- Модель вправе вернуть `speak: false`. После такого ответа не запрашиваем другие варианты для той же раздачи.
- Память: до 8 последних публичных итогов и до 5 последних опубликованных реплик, без полной истории чата.
- Проверяем дословные и близкие повторы; повторяющийся заход или метафора — причина пропуска.
- На сервере один незавершённый запрос на стол. Устаревшие события не образуют очередь.
- Частота общая для стола; персональные настройки управляют языком, голосом и громкостью. Несогласованных личных частот генерации в первой версии нет.

## 5. Какие данные видит модель

Ввести отдельный `PublicCommentaryContext`, собираемый по явному списку разрешённых полей. Нельзя отправлять модели `DealtHand`, `playerState`, `actions` или результат оценки целиком.

Разрешить: идентификатор события, номер раздачи, публичные действия без `botReason`, открытый борд, размер оспариваемых банков, публичные выплаты, чистый результат, публичные стеки, подтверждённые события, предыдущие реплики, язык.

Особенности текущего кода:

- `showdownSummary` появляется после `stage === 'showdown'`, а раскрытие карт отдельно контролирует `cardsRevealed`.
- Полный `result` и карманные карты нельзя автоматически считать доступными при завершении раздачи.
- Даже `sidePots` копируем выборочно: внутренние оценки комбинаций не нужны комментатору.
- Из `actions` исключаем внутренние объяснения бота и оценку вероятностей.
- Не передаём `fullCommunity`, сиды раздачи, токены игроков, PIN, ссылки авторизации и нераскрытые карты.

В первом выпуске комментарии строятся по выплатам и динамике стеков; конкретные карты и комбинации можно вообще не передавать. Позже добавлять их только после разрешённого раскрытия.

Правила и распределение банков остаются в `game.ts`. Если нужен новый производный игровой факт, добавить и проверить его там; модуль комментариев только отбирает и формулирует готовые факты.

Имена игроков — недоверенные данные, а не инструкции. Для первого выпуска модель использует метки участников вроде `[p1]`; сервер заменяет их допустимыми короткими именами или «игрок на втором месте». Исключить разметку и управляющие аудиотеги из подставляемых имён.

## 6. Генерация и проверка текста

Системная инструкция задаёт: русский или английский язык, 1–2 предложения, ориентир 12–22 слова и максимум 180 символов после подстановок, спокойную подачу, отсутствие советов и выдуманных причин. Модель получает небольшой список подтверждённых фактов с идентификаторами.

Предлагаемый ответ модели:

```json
{
  "speak": true,
  "text": "И хай, и лоу уходят [p1]. За столом новый лидер.",
  "factIds": ["pot1_scoop_p1", "sole_leader_p1"],
  "tone": "warm"
}
```

При `speak: false` — пустой текст и список фактов. Поля обязательны, `additionalProperties: false`; `tone` ограничен небольшим набором значений. Тон — внутренний сигнал для стиля, его не следует автоматически считать параметром выбранного TTS API.

Проверить перед озвучкой: схему, язык, длину после подстановок, допустимые метки участников, принадлежность `factIds` входному контексту, числовые значения, повторы, запрещённые утверждения о скрытых картах и намерениях. Для MVP избегать точных сумм в свободном тексте; если они понадобятся, вставлять сервером по разрешённым меткам с контролируемым произношением.

Проверка идентификаторов не доказывает, что свободный текст правильно пересказал факт. Поэтому нужен отдельный набор оценочных сценариев и ручная проверка; при неоднозначности выбираем молчание. Не обещаем математическую гарантию точности произвольной речи модели.

Ошибку схемы, отказ модели, обрезанный ответ или превышение срока обрабатывать как пропуск. Не озвучивать сырой частичный ответ. Числа и покерные сокращения нормализовать до TTS так, чтобы субтитры сохраняли тот же смысл.

## 7. Серверная цепочка

```text
Сохранённый итог раздачи
  → публичные факты
  → приоритет, пауза, наличие слушателей, бюджет
  → регистрация уникального события
  → GPT: реплика или молчание
  → проверка и подстановка имён
  → ElevenLabs: новое аудио
  → повторная проверка актуальности
  → WebSocket commentary_ready
  → локальные субтитры и воспроизведение
```

Запускать выбор события после успешного сохранения перехода в итог раздачи, во всех путях: действие человека, ход бота, таймер. Не привязывать генерацию к каждому `broadcastHandUpdated`: эта функция используется и при переподключении.

Регистрацию события делать с уникальным ключом `partyId + handId + phase`, где `phase` в MVP равен `hand_complete`. Языковые варианты имеют ключ `eventId + locale`. При нескольких процессах право обработки захватывается атомарно. Для текущего сервера достаточно SQLite и ограниченной фоновой очереди; отдельный Redis не требуется на первом этапе.

Сохранять состояние события: pending, generating, ready, skipped, failed. После рестарта старые незавершённые события помечать пропущенными, не воспроизводить заново. Доступ к провайдерам происходит вне транзакции игры и без ожидания в обработчике хода. Дедупликация публикаций не гарантирует отсутствия повторного списания у провайдера при сетевом сбое; поэтому неоднозначные запросы не повторять автоматически.

Хранить аудио вне репозитория в ограниченном временном кеше, например до 10 минут и до установленного общего размера. Приватная выдача только участникам нужной партии: проверка сессии или короткоживущая подписанная ссылка, без токена игрока в URL. Не передавать аудио в Base64 через игровой WebSocket.

Участник сообщает поддерживаемую версию комментариев, язык и режим off/text/voice через необязательное расширение подключения либо отдельное новое сообщение. Старые клиенты продолжают работать. Если слушателей нет, вызовов API нет. Синтез выполняется только для языков, у которых есть слушатели голоса; для режима text достаточно генерации текста.

## 8. Протокол и воспроизведение

Новое событие, не меняющее существующие обязательные поля:

```ts
type CommentaryReady = {
  type: 'commentary_ready';
  data: {
    id: string;
    partyId: string;
    handId: string;
    revision: number;
    locale: 'ru' | 'en';
    text: string;
    audioUrl?: string;
    createdAt: number;
    expiresAt: number;
  };
};
```

Сервер выбирает один повод; локализованные формулировки могут различаться, но опираются на те же факты. Генерация выполняется один раз на язык и событие, не на игрока. Начало воспроизведения может отличаться между устройствами из-за сети и разговоров — синхронность до миллисекунды не является требованием MVP.

Клиент принимает событие только для своей партии и отображаемой раздачи, после применения соответствующего результата. Если событие обогнало состояние, ждёт его только до `expiresAt`. Более новая ревизия сама по себе не делает итог ложным: учитывать тип изменения, а не просто равенство ревизий. Смена раздачи отменяет ожидающее или звучащее аудио.

Проигранные и пропущенные `id` запоминаются на время сессии. При reconnect старые комментарии не отправляются и не проигрываются. Смена языка не запускает повтор уже услышанного события.

Начальная цель: медиана от события до старта речи до 4 секунд, p95 до 8 секунд. Общий срок актуальности — 12 секунд с момента события; это измеряемые цели, не обещания провайдеров. После истечения срока реплика удаляется. Если тест покажет, что быстрые переходы к следующей раздаче уничтожают большую часть реплик, отдельно спроектировать короткий итог предыдущей раздачи в начале новой; не включать такое поведение неявно.

## 9. Интерфейс и голосовой чат

- Небольшой блок «ИИ-комментатор» / “AI commentator”, индикатор речи, субтитры.
- Режимы «Выключен / Только текст / Голос и текст» и громкость с сохранением выбора.
- Первое включение звука явной кнопкой пользователя; при запрете воспроизведения показать кнопку повторного запуска и оставить субтитры.
- Существующий `VoiceChat.tsx` получает `RoomEvent.ActiveSpeakersChanged`. Поднять состояние активности к общему контроллеру воспроизведения; учесть также локального участника.
- Пока говорит человек, новую реплику не начинать. После короткой паузы можно начать, если срок ещё не истёк.
- Если человек начал говорить во время комментария, плавно погасить его и пометить пропущенным; не продолжать старую фразу через минуту.
- Сигнал активности доступен при подключении к голосовому чату. Не обещать определение разговоров вне подключённой комнаты.
- На скрытой вкладке и после выхода со стола остановить звук, очистить очередь.
- При нескольких вкладках разрешить голос одному активному экземпляру стола.
- Комментатор работает и без подключения к LiveKit, например в одиночной игре с ботами.
- Компоновку проверить на обычном столе и в `mobile-table`, не перекрывать карты и кнопки действий.

Расчётный сценарий для основной связки: одна реплика на одном языке, 1500 входных токенов с инструкцией и историей, 120 выходных токенов вместе с JSON, 120 символов озвучиваемого текста.

При условных 10–20 репликах за час игры это около $0.11–0.23 на стол в час. Число игроков не умножает стоимость генерации. Если каждый раз нужны оба языка, расходы примерно удваиваются; реальное количество символов и токенов различается. Расчёт не включает налоги, инфраструктуру, неозвученные ответы модели, неудачные платные запросы и подписочные минимумы. Это модель бюджета, а не измеренный расход.

Встроить суточный лимит приложения, лимит вызовов на стол и ограничение одновременных запросов. Перед вызовом резервировать оценочную стоимость, после ответа учитывать usage; при достижении лимита пропускать комментарии. Начальные ограничения тестового запуска: до 20 попыток генерации на стол в час, суточный бюджет $5 на весь экземпляр с учётом языков. Завершение партии не обходит денежный лимит.

## 12. Надёжность и наблюдаемость

- Отдельные таймауты текста и речи внутри общего срока; ошибка провайдера не влияет на игру.
- В MVP без автоматического повтора неоднозначно завершившихся платных запросов.
- После нескольких последовательных ошибок временно отключать обращения к сервису и затем пробовать восстановление.
- При успешном тексте и ошибке TTS можно показать актуальные субтитры без звука.
- Измерять длительности генерации текста, синтеза, доставки и старта воспроизведения, токены, символы, оценочную стоимость, долю пропусков и причины.
- Не логировать целое состояние раздачи и секреты. Для проверки качества достаточно разрешённых фактов, текста, версии промпта и модели с ограниченным сроком хранения.
- Запускать за флагом функции; выключение флага прекращает новые задания и воспроизведение через состояние доступности.

## 13. Реализация по этапам

1. **Проверка сервисов и голоса.** Доступ к API и выбранным моделям, 20 фраз, 3 голоса, сравнение качества и задержки, закрепление `voice_id`. Результат: короткие образцы и измерения. Для этого этапа нужны настроенные ключи и оплачиваемый доступ; для написания модулей и тестов достаточно заглушек.
2. **Публичные факты и отбор событий.** Реализовать разрешённый контекст, корректные результаты побочных банков, паузы и дедупликацию. Результат: детерминированные тесты без API.
3. **Генерация текста.** Промпт, JSON Schema, обработка отказов, проверка текста, память и язык. Сначала режим только субтитров на тестовом столе.
4. **Синтез и серверная доставка.** ElevenLabs, временный кеш, авторизованный доступ, сроки, метрики и лимиты. Ни один вызов не блокирует игровой обработчик.
5. **Клиент.** Компонент, настройки, включение звука, взаимодействие с человеческой речью, reconnect, мобильная версия и несколько вкладок.
6. **Проверка в игре.** Автотесты, две сессии по 30 минут с людьми и ботами, настройка частоты и текста. Затем ограниченный запуск за флагом.
7. **Следующий выпуск.** Комментарии во время торгов: олл-ин и крупное публичное действие. Отдельные тесты актуальности и отсутствие стратегических подсказок; подключать только после оценки первого выпуска.

## 14. Тесты и критерии готовности

Сервер: обычный итог и scoop, несколько побочных банков, делёж хай/лоу, нечётные фишки, возврат ставки, победа без вскрытия, ничья по лидерству, вылет, досрочный конец, повторный broadcast, повтор команды, рестарт, два обработчика, отсутствие слушателей и превышение бюджета. Отдельно проверить отсутствие секретов и `botReason` во входе ИИ.

Провайдеры в автоматических тестах заменяются заглушками: неверный JSON, отказ, таймаут, HTTP 429/5xx, неполный ответ, аудио после истечения срока. Проверять поведение системы, а не точное совпадение творческой реплики.

Клиент и Playwright: два участника получают одно событие на язык; RU/EN; mute и громкость; text-only без TTS; autoplay заблокирован; человек говорит; смена раздачи до готовности звука; reconnect; скрытая вкладка; уход со стола; мобильная раскладка. Аудиопроигрыватель и события голосовой активности подменяются управляемыми тестовыми реализациями.

Качество модели: набор минимум 50 контекстов, включая редкие результаты и имена с попыткой подмены инструкции. Все выходы проверить на факты, уместность и повторы; фактические ошибки в наборе блокируют выпуск. Такой набор не гарантирует отсутствие ошибок в будущей свободной генерации. Произношение проверяется реальным прослушиванием, а не только Playwright.

Готовность: обе TypeScript-сборки и релевантные тесты проходят; игра продолжается при полном отказе обоих API; нет повторной озвучки после reconnect; закрытые данные не передаются; соблюдаются ограничения частоты и денег; задержки измерены относительно цели; русская и английская речь прослушаны.

Команды при реализации из корня:

```powershell

npm.cmd --prefix server run build
npm.cmd --prefix demo/client run build
npm.cmd --prefix demo run e2e -- commentary.spec.ts voice-chat.spec.ts reconnect.spec.ts
npm.cmd --prefix demo run e2e:mobile -- commentary.spec.ts voice-chat.spec.ts
```
